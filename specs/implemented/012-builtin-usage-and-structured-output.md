# Spec 012: Built-in Usage Visibility and Structured Output

**Status:** Complete

## Goal

Make built-in role usage and context-window consumption visible, and use provider-native Structured Outputs for built-in role responses. Keep the harness small, preserve strict local role validation and existing workflow safety, and avoid claiming unavailable measurements or provider compatibility.

## Research and current behavior

- OpenAI's [Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) documents Responses API `text.format` with `type = "json_schema"` and `strict = true` for supported models. OpenAI's [GPT-6 Luna model page](https://developers.openai.com/api/docs/models/gpt-6-luna) lists Responses, Structured Outputs, and function calling as supported; it lists a 1,050,000-token context window and a separate 922,000-token maximum input. Model limits and capabilities can change.
- The guide restricts strict schemas to a supported subset: the root must be an object and must not be `anyOf`; supported nested unions use `anyOf`. The existing `src/protocol/mod.rs` role schemas have a root `oneOf` with status-specific fields, so they cannot simply be passed through unchanged. Provider strict-schema requirements do not replace local semantic validation.
- The [Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create) documents optional response `usage`, including input, output, total, cached-input, and reasoning-output token counts. The [conversation-state guide](https://developers.openai.com/api/docs/guides/conversation-state#managing-the-context-window) describes context windows as per-request limits involving input and output. Reasoning tokens are a breakdown of output tokens; cached tokens are a breakdown of input tokens, not additional tokens.
- These sources document API/model support, not proof that this repository's ChatGPT OAuth integration, entitlement, and model accept the combination in a live request. Default tests must not require live credentials or network access; do not claim live compatibility without an observed authorized test.
- The built-in loop resends conversation input, executes shell calls sequentially, and preserves conversation state for correction-only retries. The generic role protocol validates exact typed JSON and semantic constraints locally. Pi owns its own invocation and settings.

## Requirements

### Shared cross-backend role contract

- Pi and the built-in backend use one canonical, versioned role protocol: one generated schema source per role and one exact role wire format—a top-level JSON object containing `protocol_version`, `role`, and the role's status-specific fields, with no provider wrapper. Both use the same role identifiers and protocol version, status variants, required fields, and semantic contract. Do not maintain backend-specific role schemas, versions, status policy, or semantic validators. A protocol-version upgrade is allowed only as one coordinated change applying to both backends and all roles.
- Both backends use shared normal and correction prompt construction as much as possible. Prompts present the canonical role schema and require the same canonical top-level role JSON; do not add provider-specific wrapper instructions or duplicate role policy in backend prompts. Keep genuinely provider-specific request/response transport mechanics at the backend boundary.
- Route final role JSON from both backends through the same strict local schema, role/version/status, and semantic validation path, including input-dependent evidence IDs, finding classifications, ordering, and blocked handling. Any built-in-only provider schema is a mechanical projection of the canonical schema for the provider's supported subset, never an independently authored role contract. Any provider-only envelope is transport, not role wire format: accept only its exact documented shape and normalize it at the built-in boundary before shared validation; never drop unexpected fields or infer missing values.
- Preserve existing statuses, required fields, input-dependent checks, same-role retries/correction behavior, and no-replay guarantees. A valid `blocked` response stops immediately. Provider refusal or incomplete transport is not a valid role response and must not execute or replay shell effects. Preserve Pi's effective configuration and tool surface, including Pi settings, extensions, MCP, skills, project trust, context files, inherited environment, and selected backend tools; shared protocol alignment must not add Spec Loop overrides or replace Pi execution with built-in mechanics.

### Targeted duplication cleanup

- Use one shared `PromptRole`-to-`AgentStage` mapping for both Pi and built-in backends; do not maintain backend-local copies.
- Use one review-result validation helper for plan and implementation reviews, preserving current `no_issues`/empty-findings, `issues`/finding validation, and `blocked`/reason behavior.
- Centralize checked provider retry-counter advancement at the retry boundary. Preserve existing retry eligibility, maximum retries, backoff/`Retry-After` handling, and errors; this helper must not alter retry policy.
- Keep these refactors narrow. Do not add broader abstractions or change workflow behavior.

### Usage and context visibility

- Show concise usage for each built-in role during execution, including role and selected model, provider request attempts, completed responses, elapsed time, and executed shell-call count. For each completed response with valid provider usage, show input, output, and total tokens; show cached-input and reasoning-output breakdowns when provided. Do not add breakdowns to their parent totals.
- Show cumulative role token usage across completed responses separately from the latest response's context snapshot. Count a provider request attempt whenever an HTTP request is actually sent, including retries. Count a completed response once even if its typed final handoff is invalid. Do not assume failed attempts consumed zero provider resources; explicitly label totals as observed completed-response usage rather than billing totals. Preserve available observations on failure, timeout, interruption, and correction-only continuation without replaying shell calls.
- Display latest completed response's input and output token counts as an observed per-request context snapshot, not as a cumulative role total or exact prediction of the next request. When a trustworthy context-window limit for the exact selected model is available, also show observed input plus output as a percentage of that window, explicitly labeled as the last completed response. Do not double-count reasoning tokens. Explain that a subsequent request, output reservation, separate model input limit, and provider-side accounting may change available capacity.
- Supply an optional positive built-in-only `agent.context_window_tokens` and an optional `context_window_tokens` in each existing agent stage. The global value applies only when the stage inherits the global model; when a stage overrides the model, use only that stage's explicit context-window value. A stage value overrides the global value when the model is inherited. Treat these values as user-provided limits, label them as such, and reject zero or use with Pi. Do not infer a model's limit from its name, silently use a stale model catalog, or make a new network request to obtain one. If the applicable limit or provider usage is unavailable, display `unknown` instead of inventing a percentage or token count. Counts must remain available without a configured limit.
- Treat missing or null usage as unavailable, not zero. Reject or visibly mark malformed, negative, fractional, inconsistent, or overflowing provider counts as unavailable without converting a failed provider request into success or changing role/retry outcomes. Use checked arithmetic for aggregation and percentage calculations. Do not leak prompts, output, credentials, or raw provider bodies through usage reporting.
- Do not estimate monetary cost, subscription quota, remaining provider access, or price from token counts. No automatic compaction, truncation, model switching, or tool-call limit is introduced by usage reporting.

### Provider-native structured role responses

- For built-in roles, use the documented Responses API strict `json_schema` text format derived from the shared role contract, including correction-only requests. Continue exposing the existing shell tool and execute tool calls only after validated completed provider responses, sequentially and without replay. Keep workflow policy and the canonical role protocol provider-independent.
- Derive the provider-compatible schema from the existing role schema or its typed source; do not maintain a separate hand-written copy of role policy. If a transport wrapper or nullable fields are needed for the provider's strict subset, normalize only that explicitly defined transport into the existing canonical role JSON. Do not drop unexpected fields, infer missing status, invent values, or weaken canonical role shape or semantic checks. Preserve all existing statuses, `blocked` semantics, required fields, input-dependent checks, role/version checks, and finding order constraints.
- Where the provider subset cannot express an existing constraint, retain and enforce that constraint in existing local validation. Preserve same-role typed-response correction behavior and correction-only no-tool behavior. A valid `blocked` response still stops immediately. A refusal or incomplete provider response is not a valid role response; report it actionably without treating it as success or rerunning completed shell effects.
- If the selected model, OAuth authorization path, or provider rejects the structured format or schema, fail with actionable diagnostics and preserve completed effects. Never silently fall back to a weaker response format, another provider, or API-key authentication. Do not claim unsupported models or ChatGPT entitlements work. Keep Pi's effective settings, tools, invocation, inherited environment, and retry behavior intact while bringing its role prompt and response through the shared protocol.

### Documentation

- Update README and applicable CLI/configuration help and examples for usage, optional context-window settings, stage-model precedence, provider limitations, and `unknown` values. State that reported token usage is observed API data, not a cost, quota, or exact forecast. Document Structured Outputs and continued local validation; do not claim live OAuth compatibility without actual evidence.

## Acceptance criteria

1. Deterministic fake-provider tests cover multiple requests and tool calls, retries, correction-only continuation, success, blocked responses, failure, timeout, and interruption. They verify role-scoped attempt/call counts and observed usage without replaying completed commands.
2. Tests cover missing/null usage, optional breakdowns, zero and large valid counts, malformed/negative/fractional values, inconsistent breakdowns and totals, and arithmetic overflow. Unavailable values are explicit and never reported as zero or a fabricated cost.
3. Tests distinguish cumulative usage from the most recent per-request context snapshot, verify cached and reasoning breakdowns are not double-counted, and cover configured/unknown limits, separate stage model overrides, invalid limits, and Pi rejection. Percentage output identifies a user-supplied limit and never claims to predict next-request capacity.
4. For every role and status, offline tests prove Pi and built-in use the same generated canonical schema, versioned top-level JSON wire format, and shared strict local validation path. Fake Pi and provider responses exercise identical valid, malformed, semantically inconsistent, and input-dependent values; both accept/reject identically, including blocked handling and finding/evidence order. Any built-in provider schema is mechanically derived from the canonical schema, and any API envelope is normalized only at the built-in boundary before shared validation.
5. Fake backend tests prove normal and correction prompts share the same canonical role instructions/schema for Pi and built-in. Fake HTTP tests also inspect Responses requests for strict role-specific `text.format`, retain shell tool definitions and normal tool-loop sequencing, and cover correction-only requests. Test refusal, incomplete responses, unsupported model/schema errors, and malformed structured responses; none may count as successful completion or replay prior shell commands.
6. Pi's effective settings, tools, extensions/MCP/skills/trust/context, inherited environment, and execution behavior, plus selected-spec/plan integrity, provider retry limits, agent timeouts, cancellation, shell execution, and run-log security remain intact. Tests require no live model, credentials, Git installation, network access, or developer worktree state.
7. Documentation and examples match implemented behavior and parser. Run `make check` after implementation. An optional user-authorized live OAuth smoke test may provide compatibility evidence but is not part of default CI and must not be represented as passed unless actually run.
8. Targeted duplication cleanup is verified: every `PromptRole` maps to the same `AgentStage` for Pi and built-in; plan and implementation review use the same review-result validator with existing outcomes; provider retry counter advancement remains checked and preserves attempt limits, retry delays, and behavior across retryable failure paths. Tests cover the shared routing and validation plus existing provider retry vectors.

## Non-goals

- Charging or cost estimation, subscription usage guarantees, provider billing integration, or an automatically maintained model catalog.
- Changing Pi's effective settings or tool surface, workflow role requirements, check/review gates, or shell sandboxing. Shared role-protocol alignment is in scope; provider-specific execution mechanics remain isolated.
- Automatic context compaction, tool-result truncation policy changes, new model tools, or replay of side-effecting calls.
